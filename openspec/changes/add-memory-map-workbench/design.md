## Context

现在有两个对话框共用一个后台任务类：

- `MemoryMapCheckDialog`（`memory_map_check_dialog.py`）：设置（两个目录列表、链接文件）、扫描、按类别的结果树、导出清单；设置随工程保存。
- `MemoryLayoutDialog`（`memory_layout_dialog.py`）：没有自己的设置，从工程读同一份；自己再启动一次 `_CheckWorker`；按区域／模块的树、过滤、详情、导出。它从检查窗口模块里导入 `_CheckWorker` 和 `ALL`，依赖方向本身就说明两者其实是一个界面。

两者读的是同一个 `CheckResult`。布局页签用到 `result.rows`，诊断页签用 `result.findings`。`SectionRow.findings` 只收经过 `report()` 的发现（放置相关的 `UNPLACED`、`MULTIPLE`、`WILDCARD`、`CORE`、`CACHE`、`FLASH`），而 `UNMAPPED`、`USAGE`、`DUPLICATE`、`SYMBOL` 四类直接进 `result.findings`。这是“布局看起来正常”的来源，不是界面的 bug，是数据模型的边界。

## Goals / Non-Goals

- Goals：一个窗口、一次扫描、两个页签；任何发现都能在布局页签里被看到或被明确告知"在诊断里"；每条发现有固定的严重程度。
- Non-Goals：新增检查；编辑放置；改变 `CheckResult` 已有字段的含义。

## Decisions

### D1 一个窗口，页签而不是并排

诊断是"一条一条看问题"，布局是"一屏看全貌"，两者都要用到宽度，并排会让两边都挤。页签切换成本低，且共享顶部的设置与进度。窗口大小沿用布局窗口的 1200×780。

### D2 没有对应段的发现，在布局页签用一行汇总承接

不把这四类发现硬塞进某个段行：它们本来就不属于一个输出段（未映射的段没有输出段，链接符号缺失属于执行区域，写法问题属于源文件）。做法是：

- 布局页签顶部一行：`另有 N 条发现不对应某个输出段（错误 a、警告 b、提示 c），在“诊断”页签查看`，带一个按钮切到诊断页签并过滤到这几个类别；
- 汇总不受布局过滤影响。过滤的是段，不是整个结果。

这样"只看有问题的"仍然只管段，但用户不会因为它而漏看别的问题。

### D3 严重程度由类别决定，在一处定义

`check.py` 里一张 `SEVERITY` 表：类别 → 错误／警告／提示。`Finding.severity` 是一个派生属性：先取类别对应的级别，若 `possible`（在 `#if` 分支里）则降一级。不把级别存进 `Finding` 里作为字段，避免它和类别、`possible` 三处不一致。

分级依据（不是主观偏好）：

| 类别 | 级别 | 依据 |
|---|---|---|
| 用到但没有映射 | 错误 | 编译触发 MemMap 的 `#error` |
| 链接符号缺失 | 错误 | 链接阶段符号未定义 |
| 数据段放在 flash | 错误 | 数据在 flash 里不可写，运行时必然出错 |
| 段声明写法问题 | 错误 | START/STOP 不配对会让后续所有段归属错乱 |
| 没有区域接收的段 | 警告 | 链接器可能报错，也可能被其他规则吸收，静态无法确定 |
| 被多个区域显式选中 | 警告 | 链接器取哪个由规则决定 |
| 核心数据不在本核心内存 | 警告 | 依赖段名里的核心号和芯片区域数据，后者可能待确认 |
| 不可缓存的段在可缓存内存 | 警告 | 同上，依赖段名约定 |
| 重复映射 | 警告 | 可能是有意的覆盖，也可能是误拷 |
| 未显式放置的段 | 提示 | 仅被通配接收，是常见的合法写法，静态推断 |

对"段声明写法问题"定为错误，我不是很有把握：真实头文件里有大量历史写法（宏被条件编译包住等），可能产生很多误报。因为这类发现已经有"可能"降级，所以先定为错误，看真实数据后再调整，这是 Open Question。

### D4 页签之间的定位靠“键”，不靠行号

诊断条目带 `(类别, 路径, 行, 文本)`，布局的段行带 `output`。定位的做法：

- 诊断 → 布局：条目的 `Finding` 如果出现在某个 `SectionRow.findings` 里（按对象身份），就切到布局页签、清掉过滤、选中那一行；否则按钮置灰，提示"该发现不对应某个输出段"。
- 布局 → 诊断：详情里列出该段的发现，点击一条切到诊断页签并选中同一个 `Finding`。

用对象身份而不是按文本匹配，因为同一文本可能在不同位置重复。

### D5 一次扫描，设置变化后结果标为过时

窗口记录扫描时的设置快照（源码目录、头目录、链接文件）。设置与快照不同时，结果区域上方显示"设置已改动，结果可能过时，请重新开始"，结果仍可看。不自动重扫：扫描可能要几十秒。

### D6 合并是替换，不是共存

旧的两个窗口和菜单项删除，不保留。理由：保留会让用户困惑，且维护两套。已有测试迁移，而不是删除：行为的断言全部保留，只换对话框类。

## Risks / Trade-offs

- **严重程度的分级是我定的，不是用户定的。** 先给出一版并写明依据，用户可以改表。表在一处，改动成本低。
- **合并会让窗口变大，代码集中到一个文件。** 把 `_CheckWorker`、目录列表控件、两个页签拆成三个类，各自可单独测试；不把所有逻辑塞进一个 `QDialog`。
- **迁移已有 UI 测试。** 三个测试文件共 20 多个用例，迁移时容易漏。迁移后用例数不得少于迁移前，作为完成条件。
- **页签定位依赖对象身份。** 结果重新扫描后旧选中失效，窗口在新结果到来时清空选中。

## Migration Plan

1. 先加严重程度和汇总（核心层，不动界面），测试通过。
2. 新建工作台，两个页签先各自复制现有逻辑，跑通迁移后的测试。
3. 删除旧对话框和菜单项，更新主窗口。
4. 全量测试。回退办法：在提交前，旧文件还在版本库里，可以整体还原这几个文件。

## Open Questions

- "段声明写法问题"定为错误是否合适：需要在真实数据（T1 或厂商目录）上看误报率，再决定。这一步要读厂商文件，运行前先征得用户同意。
- 严重程度要不要允许用户在界面里调整，还是固定？本变更先固定。
- 工作台是否要把"芯片区域待确认"这类提示放到顶部固定显示，而不是混在底部的说明里？现在两处都显示在窗口底部，容易被忽略。
