## Context

读到的现状（读文件，未运行）：

- 厂商 `LinkerAdsPf.scat`：一个加载区域 `ROM_CODE`，里面按顺序排执行区域；起点用 `AlignExpr(ImageLimit(前一个), 64)`；相同存储里的区域一个接一个；每个数据区域后面跟一个 `<名>_LIMIT … EMPTY 0x0 {}` 的界限区域（文件末尾集中写）；栈区域是 `EMPTY 0x1000 {}`；
- 选择器的写法：`*(.name)` 显式、`*(+RO-DATA, .name)` 带属性、`*(+BSS)` 通配；
- 同一个文件里还有为未启用的核（CORE2、CORE3）写的"保留区域"（`EMPTY 0x0 {}`，接在 LMU3 之后），注释写着 `reserved region for compiler issue`：`startup.c` 引用了这些名字，链接器要有定义才能通过；
- 符号对应：ADS 的 `Image$$<名>$$Base` 等来自执行区域名，`Image$$<名>_LIMIT$$Base` 来自 `<名>_LIMIT` 空区域（`add-link-symbol-needs` 的事实）。

注意最后一点：厂商原版 `startup.c` 引用了 CORE2、CORE3 的区域，而 THA6206 只有 2 个核，厂商脚本为此写了"保留区域"让链接通过。如果生成的链接文件没有这些区域，直接使用原版 `startup.c` 会链接失败。

**但 `startup.c` 是用户手写和维护的代码，这个工具不生成它**（用户已确认）。所以这不是生成器必须迁就的固定约束，而是一个**可选项**：用户用原版 `startup.c` 就需要保留区域，改掉了对未启用核的引用就不需要。

## Goals / Non-Goals

- Goals：编译器无关的链接计划；ADS 生成器；生成后自检；界面里选编译器并生成；THA6206。
- Non-Goals：其他编译器的生成器；容量检查；OS 自带 scatter 的处理。

## Decisions

### D1 链接计划与语法分离

```
布局配置 + 芯片 + 链接符号需求
          ↓
      链接计划 (Plan)        ← 编译器无关
          ↓
   生成器 (ADS / GHS / …)    ← 每种编译器一个
          ↓
      链接文件文本
```

**链接计划**的内容：

- 加载区域列表（名称、基址、大小上限）；
- 执行区域列表：名称、所在加载区域、起始（`Absolute(addr)` 或 `After(前一个区域, 对齐)`）、种类、对齐、收纳的输出段（按名称排序）、是否需要界限区域；
- 保留区域列表（见 D3）；
- 每个必需区域需要的符号集合（用途，不含语法）。

生成器只读计划，不读布局配置，也不做放置判断。这样新增一种编译器只需要加一个生成器，放置逻辑不会被复制。

实现时定下的细节（`core/memmap/plan.py`）：

- **一个加载区域** `ROM_CODE`（厂商的名字），基址是第一个 flash 窗口，大小上限取该窗口的大小；
- **窗口顺序**：先 flash 窗口，再按窗口起始地址；窗口内按区域的 `order`，同序再按名称。不依赖配置文件里区域的书写顺序，所以同样的配置得到同样的计划；
- **段**：只收 `place_all` 状态为"规则"与"手动"的段，按名称排序；
- **大小上限**：没有容量信息。执行区域的大小上限取出厂布局条目的 `size`（目前 THA6206 的出厂数据里没有这一项），没有就写窗口的大小；栈区域的长度同样先取布局，没有就用厂商的 `0x1000`；
- **界限区域**：需求里有"界限"或"清零"用途（`RegionNeed.needs_limit_region()`）的区域标记需要界限区域；代码直接写 `<R>_LIMIT` 名字的，也标记 R。**没有扫描到任何引用区域名的代码时**，不知道哪些区域需要界限，就给每个区域都写界限区域（多出的空区域无害，缺了链接失败），并给出警告；
- 计划里还带每个区域在代码里的用途（不含语法），供以后的生成器取符号。

### D2 为什么先只做 ADS

- ADS 已有解析器、检查器、厂商样例和符号表，生成后能立刻用现有工具验证；
- GHS 的符号约定已读，但文件格式（`MEMORY`/`SECTIONS` 块的写法）我没读，**不应该凭想象写生成器**；
- HighTec（`.ld`，GNU ld 风格）、IAR（`.icf`）、Tasking（`.lsl`）我只看到了文件名。

所以 ADS 之外的编译器在生成器登记表里登记为"尚未支持"，界面据此置灰。每增加一种，都需要先读那种格式的厂商样例并写它自己的对照测试，这在各自的变更里做。

### D3 保留区域：可选，默认开

`startup.c` 里引用 CORE2、CORE3 的区域，而 THA6206 没有这两个核。`add-memory-layout-config` 里这些区域按核数被裁剪、不进配置，用户在配置界面里看不到不存在的核的区域。生成链接文件时怎么处理，取决于用户用的 `startup.c`：

- 用原版：需要这些区域，否则链接时符号未定义；
- 用户改过、不再引用：不需要，多写几个空区域也无害，但文件里多出无用的名字。

所以做成**生成选项"为未启用的核写保留区域"，默认开**，存在配置的 `options.reserve_missing_cores`（没有这一项即为开）。理由：默认开时，最常见的情况（用厂商原版 `startup.c`）直接能链接；用户改了 `startup.c` 可以关掉。默认关则相反，最常见的情况反而会链接失败，错误要到链接时才暴露。

选项开着时，链接计划在被裁剪的必需区域（配置的 `trimmed`，按名称排序）上加"保留区域"：`EMPTY 0x0 {}`，起点 `AlignExpr(ImageLimit(<最后一个执行区域>), 64)`，不含任何段，只为让符号存在；代码需要它的界限时，同样写一个 `<名>_LIMIT` 空区域。这与厂商脚本做法一致。保留区域**不出现在配置界面**，只出现在生成的文件里，文件里用注释标明"为未启用的核保留；若 startup.c 不引用可关闭此选项"。选项的值随工程保存。

这里不再需要去核对 `startup.c` 在 2 核芯片上是否编译那些分支：保留区域多余但无害，缺了反而可能出问题，所以默认开是安全的一侧。

### D4 ADS 生成器的输出规则

- 第一行与厂商脚本一致；
- 区域基址用 `#define 名 地址`，名字取物理存储窗口名加 `_ADDRESS`（与厂商一致，如 `GMU_NORMAL_ADDRESS`），只为放了区域的窗口写；
- 执行区域按计划的顺序写，起点：绝对地址用 `#define` 名，接续用 `AlignExpr(ImageLimit(前一个), 对齐)`；
- 选择器：每个输出段写 `*(.name)`；区域里的段按名称排序；
- 界限区域：每个需要的区域后面（集中放在文件末尾，与厂商一致）写 `<名>_LIMIT AlignExpr(ImageLimit(<名>), 对齐) EMPTY 0x0 {}`；
- 栈区域：`名 起点 ALIGN 对齐 EMPTY 大小 {}`，对齐取区域的对齐（出厂布局为 8），大小见 D1；
- 普通区域：`名 起点 ALIGN 对齐 大小上限`，大小上限见 D1；
- 每个窗口前写一行 `;窗口名` 注释，与厂商一致；保留区域前写注释说明为何存在、`startup.c` 不引用时可关闭；
- 注释行写"由内存映射工具生成"、配置文件名和芯片名，不写时间戳——**同样的输入必须得到逐字节相同的输出**，指纹才稳定。注释只用 `;` 行、不含引号和撇号（文件先经 C 预处理）；
- 行尾统一 `
`，UTF-8 编码。

### D5 生成前拒绝的条件和只警告的条件

拒绝（不写文件，列出原因）：

- 有"待重新放置"的段：它们指向不存在的区域，生成出来的文件不可信；
- 必需区域没有落到任何窗口：生成不出起点；
- 配置里引用的窗口在当前芯片里不存在。

只警告（写文件，预览里列出）：

- "未放置"的段：它们会被链接器的通配区域接走或不被接收，由用户知道就行；
- 默认布局的必需区域"未经代码核对"：配置里没有记下必需区域的来源（`Prepared.required.source` 不保存），所以以"没有扫描到任何引用区域名的代码"为准发出这条警告；
- 代码引用了某个区域名，但配置里既没有它也不在 `trimmed` 里：生成的文件里不会有它，自检会报"链接符号缺失"。

另外，配置里一个执行区域都没有落在芯片窗口上时也拒绝（生成不出任何东西）。

### D6 生成后立即用检查器验证

生成物被当作链接文件传给 `run_check`，结果显示在界面。验收：在"链接符号缺失"和"没有区域接收的段"上没有发现。这是整个"收集、匹配、生成、回头检查"流程里的最后一环（第 5 步）。

这也是一个自洽性检查，**不是正确性证明**：检查器和生成器都是我写的，两边共同的误解它发现不了。它证明的是"配置与生成物一致"，与任何厂商脚本无关。最终正确性要靠在编译器里真正链接（工具外，需要用户）。

### D7 厂商脚本不是标准答案（由 update-linker-generator-authority 修订）

原设计在这里把厂商 `LinkerAdsPf.scat` 当作对照基准。用户 2026-11-03 定位：**生成器是权威**，工程里的配置是链接文件的唯一来源；厂商脚本只是一个可有可无的、选择性的导入源，没有它也能靠人工配置生成。

因此：

- 不再把"与厂商脚本对照"作为验收条件；
- 生成结果与厂商脚本不同时，不当作生成器的错误，而是看配置能否表达用户想要的布局（起点、大小、加载区域、界限对齐等），缺什么就补什么能力；
- 厂商脚本可以通过"从链接文件导入"（`update-linker-generator-authority`）变成配置的起点，之后照样可以改。

### D8 写文件

- 目标目录 `IntegrationProject/linkedFile/Ads/`，文件名 `scatter.scat`；
- 已有同名文件：先备份为 `scatter.scat.bak`，再写；
- 先写临时文件再改名，避免写一半失败留下残缺文件；
- 写的路径、字节数、是否覆盖，都在预览里先给用户看。

实现（`core/memmap/linkfile.py`）：`prepare_generation` 只计划、检查、生成文本，不写；`preview` 是纯函数（路径、是否覆盖、备份路径、UTF-8 字节数、内容是否与现有文件相同）；`write_linker_file` 按顺序：在同目录写临时文件 → 复制旧文件为 `.bak` → 改名到位。临时文件写失败时旧文件和 `.bak` 都不动；任何失败都删掉临时文件。用户取消即不调用 `write_linker_file`，不留任何东西。`self_check` / `self_check_text` 把文件（或尚未写的文本的临时副本）交给 `run_check`。

## Risks / Trade-offs

- **ADS 之外全部没有。** 用户选了别的编译器会看到置灰。这是有意的：不做没读过格式的生成器。
- **保留区域默认开**（D3）：用户改过 `startup.c` 后文件里会多几个无用的空区域，可关掉。
- **生成与检查同出一手。** D6 已说明，只能证明自洽，不能证明正确。最终正确性要看真实链接。
- **没有容量信息，生成的文件可能超出存储。** 生成不检查，编译器链接时会报，这是你同意暂不考虑的。
- **默认栈大小**：由 `update-linker-generator-authority` 改为可配（区域的 `size`）。

## Migration Plan

1. 先做链接计划（核心层，不碰文件）；
2. 再做 ADS 生成器，用合成配置验证输出；
3. 再做界面和写文件；
4. 由用户在 ADS 里实际链接一次（工具外）。
回退：生成的文件是新增的，删除 `linkedFile/` 目录即回到现状。

## Open Questions

- 生成选项还有哪些值得开放：栈大小、是否写 `*(+BSS)` 这类通配选择器、对齐值。本变更只开放保留区域一项。
- 其余四种编译器何时做、先做哪一种。
- 生成的 `.scat` 与 OS 自带 `scatter.scat` 并存时，工程里哪个才是最终使用的链接文件：由用户的工程文件决定，工具不管；但两份里区域名重复时可能混淆，下一阶段处理。
- 栈大小是否需要开放给用户编辑。
