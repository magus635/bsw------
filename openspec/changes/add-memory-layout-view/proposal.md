## Why

`add-memory-map-check` 能报出"哪些段放错了"，但结果是按问题类别排列的清单，集成者看不到全貌：某个物理区域里放了哪些模块的哪些段、某个模块的段分散在哪些区域。要改放置，又得回到链接文件里手工修改。

目标是把 OS、MCAL、SDK、RTE、应用的段信息集中到一个界面，像集成开发环境那样看、最终也能在这里配置。整体路线见 `design.md`，本变更只做第一步：**只读的统一视图**，不改任何配置和文件。

## What Changes

- **新增"内存布局"视图**，数据来自 `add-memory-map-check` 已经取到的三部分：用到的段、MemMap 头的映射、ADS 分散加载文件的放置，再加芯片 `memory_regions`。
  - 一行一个输出段：输出段名、种类（TEXT/RODATA/DATA/BSS）、来源模块、核心、是否可缓存、用到的位置、当前落在哪个执行区域和芯片区域、是显式放置还是被通配接收、有没有问题。
  - 两种组织方式可切换，默认按物理区域：
    - **按物理区域**：芯片区域 → 执行区域 → 段。
    - **按模块**：模块 → 段，每个段标出落在哪个区域。
  - 过滤：按模块、核心、种类、"只看有问题的"。
  - 每个有问题的段旁边显示对应的检查结果（未映射、未显式放置、核心不符、缓存不符等），选中后可看到来源文件和行。
- **检查补充两项**（视图要能展示的问题）：
  - 同一输出段被多个执行区域显式选中（现在只取第一个，其余静默忽略）；
  - DATA、BSS 段落在芯片 `type: flash` 的区域。TEXT 放进 RAM 是合法的（如厂商的 `RAM_CODE`），不报。
- **导出**：视图可导出 Markdown 表格，按当前组织方式和过滤结果。
- **来源模块**取自段名 `<X>_START_SEC_<Y>` 里的 `<X>`。RTE 生成的代码用同一套宏，把它的目录加为源码目录即可显示；本变更没有 RTE 样例，不做 RTE 专门的适配。
- **界面**：在"检查内存映射"对话框旁新增"内存布局"窗口，沿用其后台执行、可取消的做法，使用同一份工程设置（源码目录、MemMap 头目录、链接文件）。

## Impact

- Affected specs：`memory-layout-view`（新增）
- Affected code：
  - `core/memmap/check.py`：结果里新增"段行"（每个输出段的属性和放置），新增重复放置、flash 类型两项检查
  - `core/memmap/scatter.py`：`placements()` 返回全部显式放置，不只取第一个
  - 新增 `core/memmap/layout.py`：由检查结果按物理区域、按模块组织视图数据，不依赖界面
  - 新增 `ui/dialogs/memory_layout_dialog.py`，并在主窗口挂菜单项
- **兼容性**：只读，不改变生成结果；`CheckResult` 只新增字段，现有的"检查内存映射"对话框和导出不受影响。
- **依赖**：本变更依赖 `add-memory-map-check` 已实现的 `core/memmap/`。该变更的任务 7.1（T1 上由用户确认结果）仍未完成，本变更可以并行开发，但视图的验收要用同一份 T1 结果。
- **不在本变更范围内**（见 `design.md` 的路线）：读取"链接符号需求"（`startup.c`、OS MPU 代码引用的区域名）；集成者层面的布局配置存储及其编辑；按编译器生成链接文件；ADS 以外编译器；RTE 专门的适配。本变更不修改任何模块的配置。
