## Context

`add-memory-map-check` 把三类信息读出来并比对：段的使用、MemMap 映射、链接文件的放置，再按芯片 `memory_regions` 判断属性。它的输出是按问题类别排的清单。

集成者要的是另一种视角：把 OS、MCAL、SDK、RTE、应用放在一起看全貌，并最终在同一个地方调整。方向是：**从各模块配置生成的代码或源码里读取内存信息，与芯片物理内存匹配，再按编译器生成链接文件**；集成者只在统一界面里表达放置意图，不去改各模块的配置。

早先考虑过由工具把意图翻译成对 OS 配置的联动修改，后来放弃了。放弃的原因是 OS 配置里这些项互相牵连（已核实，来自 `Os.xdm` 与 OS 模板）：

- `Os_link_Lcfg.c` 模板多处把区域名写死为 `PFLASH0`、`PFLASH1`，区域改名后初始化表的 flash 拷贝部分失效且无报错。
- 栈引用的区域不能是 FLASH，也不能是名字含 `GMU` 的区域（`Os.xdm` 里该校验写在 `INVALID` 下，表达式为真即报错），所以栈只能放在核本地的 RAM（如 TCM）。这条规则本身合理，不是放弃联动修改的理由；同一校验的第二条按区域名里的数字（`'1'`、`'0'`）判断"别的核的内存"，依赖命名约定，比较脆弱。
- 核心相关字段写死为 Core0、Core1，`MemoryRegionCopy` 取值只到 CORE1。
- scatter、初始化表、MPU 都由同一组 OS 配置生成（MPU 一条未核实）。

## Goals / Non-Goals（本变更）

- Goals：在不改任何配置的前提下，把已有检查数据组织成统一视图，让集成者看到全貌和问题所在；验证"段 × 区域"这个模型是否够用，再决定后续步骤做多深。
- Non-Goals：读取或修改 OS 配置；保存集成者布局；生成链接文件；RTE 适配。

## Decisions

### D1 视图数据与界面分离

`core/memmap/layout.py` 只产出数据结构，界面只负责展示。这样视图逻辑可以不用显示环境测试，后续步骤（编辑、生成）也能复用同一个模型。

数据结构：

- `SectionRow`：输出段名、种类、来源模块集合、核心（可空）、是否不可缓存、使用位置、放置（执行区域、通配选择器或显式、芯片区域，可空）、关联的检查结果。
- `RegionGroup`：芯片区域名（或"未识别"）、属性（核心、是否可缓存、类型）、其下的执行区域，每个执行区域含其中的段。

按物理区域和按模块是同一批 `SectionRow` 的两种分组，不是两套数据。

### D2 一个输出段可对应多个来源模块

不同模块的头可以把各自的段映射到同一个输出段（例如多个驱动都用 `.mcal_bss_asil_d_unspecified_core0`）。视图以**输出段**为行，来源模块是集合。按模块分组时，同一输出段会出现在每个来源模块下。这与链接文件的视角一致：链接器只认输出段。

### D3 来源模块取自段名前缀

`<X>_START_SEC_<Y>` 的 `<X>` 就是模块。不额外维护"哪个模块属于 MCAL、SDK 还是 OS"的分类，避免再引入一份需要同步的表。需要分类时，用户按目录区分（源码目录是用户添加的）。

### D4 "有问题"直接复用检查结果

视图不重新判断问题。`SectionRow` 持有检查产生的 `Finding`，过滤"只看有问题的"就是看它是否有关联结果。两个界面看到的是同一个结论。

### D5 重复放置与 flash 类型是检查的补充，不是视图的逻辑

两项都加在检查里，视图只展示。这样"检查内存映射"对话框和导出也能得到它们。

- 重复放置：`placements()` 的显式结果多于一个时，报告全部区域。链接器会取哪一个取决于其选择规则，所以只报告，不判断哪个对。
- flash 类型：只检查 DATA、BSS，因为 TEXT 放进 RAM 合法。NO_INIT 在 MemMap 里属于 BSS 种类，同样检查。
- 芯片没有 `memory_regions` 时两项中的 flash 类型检查跳过，重复放置不依赖芯片数据，照常检查。

## 路线

整体流程是：**从代码收集 → 与芯片物理内存匹配 → 按编译器生成链接文件 → 回头检查**。MCAL、SDK、OS、RTE 一视同仁，都从配置生成的代码或源码里读取内存信息，不要求集成者去改各模块的配置。

1. **本变更（收集的一部分 + 只读视图）**：统一视图，只读。
2. **收集补全**：除了段的使用和映射，再读"链接符号需求"，即链接文件必须提供的区域名。
   - MCAL/SDK：厂商 `startup.c` 里 `STARTUP_GETCOPYDATAINFO(UNDEFINE_RAM_DATA, …)`、`STARTUP_GETBSSDATAINFO(…)` 引用的区域名；
   - OS：生成的 `Os_mpu_Lcfg.c` 里 `Image$$OS_CORE0_STACK$$Base` 这类符号，以及生成的 `Os_memmap.h`（94 条映射，现有扫描器可直接读）。
3. **匹配与布局配置**：段对芯片 `memory_regions`，界面里看到哪些段无处可放；集成者的放置决定存为新的布局配置，默认规则 `COREn` 进 CPUn BTCM，`uncached` 进 DEVICE，CODE、CONST 进 PFLASH。界面按"芯片物理内存 / 区域里的段 / 未放置的段和问题"组织，可选择或拖动改放置，改完即时重新检查。
4. **按编译器生成**：每种编译器一个生成器（先 ADS `.scat`，再 GHS `.ld` 等），必须产出第 2 步读到的全部区域名，并保留 `*_LIMIT` 空区域约定；厂商 `LinkerAdsPf.scat` 作对照基准。
5. **回头检查**：用本变更的检查器验证生成结果，应当没有"未显式放置""没有区域接收"等问题。

之后：启动初始化表检查；按 map 文件检查容量（界面的用量条依赖它，代码里没有段的大小）；THA6412 四核。

**原路线中"编辑 OS 的块时联动改 OS 配置"不再作为目标**：OS 的段从 `Os_memmap.h` 读，放置由集成者布局决定，不需要集成者去改 OS 配置里互相牵连的多项参数。事实来源因此只有两处：各模块的生成代码（读），集成者布局配置（写）。

已核实的前提（读文件，未运行）：
- 厂商 `startup.c` 与 OS 的 MPU 代码都按固定区域名引用链接符号，所以生成链接文件必须产出这些名字；
- 厂商 `startup_ads.h`、`startup_ghs.h` 各有一套宏隐藏符号命名差异。GHS 的约定还没读，做多编译器之前要先查；
- `output/` 里的 `Os_link_Lcfg.c` 只有注释，`Os_mpu_Lcfg.c` 的地址全为 0，说明那份输出的 OS 内存没配好，不能当参照。

## Risks / Trade-offs

- 视图的价值取决于检查数据是否准：漏加目录就会漏段。结果头部沿用检查的做法，列出扫描的目录和文件数。
- 一个输出段对应多个模块时，"按模块"视图里同一个段出现多次，行数会多于输出段数。在视图标题显示的是输出段数，避免误导。
- 芯片区域数据待确认：沿用检查的做法，在视图顶部注明，并不隐藏任何区域。
- 本变更的 RTE 支持只是"把目录加进来就能显示"，没有样例验证。

## Open Questions

- **第 4 步生成的链接文件，是替换 OS 自带的 `scatter.scat`，还是只生成 MCAL/SDK 部分、OS 部分保持原样？** 替换则 OS 原来那份要停用，OS 的初始化表（`Os_link_Lcfg.c`）必须与新链接文件一致；它怎么依赖区域名还没核实。保持原样风险小，但 OS 和其他部分仍分在两个文件里。需要用户决定。
- 第 3 步集成者布局配置存在工程文件里，还是单独文件（便于多人共享、纳入版本管理）。
- OS 模板的疑似缺陷（`scatter.scat` 第 210 行 `concat` 缺逗号、第 77 行 `node:name` 误用）只在第 4 步选择"替换"时才相关，到时再去 `19_AutosarOS` 插件里确认。
