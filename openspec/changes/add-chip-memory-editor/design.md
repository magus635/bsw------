## Context

现有 `memory_regions`（`add-memory-map-check`）是平铺的：`name、start、size、type、core、cacheable`。THA6206 的 25 项来自厂商脚本头部的注释表，那张表里同一块物理存储常有多个地址窗口：

| 物理存储 | 窗口 | 地址 | 可缓存 | 核心 |
|---|---|---|---|---|
| PFLASH0 | `CPUXPFLASH0` | `0x08000000` | 是（待确认） | 本地 |
| PFLASH0 | `PFLASH0_NORMAL` | `0x40400000` | 是 | 共享 |
| PFLASH0 | `PFLASH0_DEVICE` | `0x90400000` | 否 | 共享 |
| GMU | `GMU_NORMAL` | `0x10000000` | 是 | 共享 |
| GMU | `GMU_DEVICE` | `0x82000000` | 否 | 共享 |
| CPU0 BTCM | `CPU0BTCM` | `0x30100000` | 否 | 核 0 |
| CPU 本地 BTCM | `CPUXBTCM` | `0x00100000` | 否 | 本地 |

（上表前五行是厂商脚本里直接读到的名称与地址；"CPU 本地 BTCM 与 CPU0 BTCM 是同一块存储"这一点是我从名称推断的，厂商表里没有明说，所以导入后这类归组一律标待确认，由用户核对。）

后面"段放进哪里"的界面要按"一块存储 → 选窗口（决定缓存与否）"来呈现，所以数据模型必须能说出"这几项是同一块存储"。

## Goals / Non-Goals

- Goals：在设计器里编辑详细的物理存储；模型能表达一块存储的多个窗口；能从 ADS 脚本注释表导入；旧数据与旧芯片的行为不变。
- Non-Goals：给 THA610X、THA6412 填数据；存储的非地址属性（ECC、等待周期、访问宽度）；非 ADS 脚本的导入。

## Decisions

### D1 平铺列表不变，分组靠可选字段

不引入嵌套结构（`memories: [{name, windows: [...]}]`）。理由：

- 现有检查、`region_at`、YAML 往返、`chip_checksum` 都按平铺列表工作；嵌套要改所有这些，而且旧 YAML 要迁移。
- 平铺加 `memory` 字段，是纯增量：没有该字段的项照旧，旧文件不动，`chip_checksum` 对旧芯片不变。

代价：分组关系分散在各项上，改存储名要改多项。编辑器按存储分组显示、按存储重命名（一次改所有窗口）来缓解。

### D2 字段

| 字段 | 必填 | 含义 |
|---|---|---|
| `memory` | 否 | 所属物理存储名；缺省时等于该项的 `name`，即单窗口存储 |
| `window` | 否 | 窗口用途标签：`local`、`normal`、`device`、或自由文本；仅显示 |
| `source` | 否 | 数据来源说明，自由文本 |

序列化时只写有值的字段，且 `memory` 等于 `name` 时不写（保持旧格式的最小输出）。

### D3 校验分两级：阻止保存的与只提示的

阻止保存：数字格式错误、大小不为正、名称重复、类型不是 flash/ram。这些在 `parse_memory_regions` 里本来就是 `ValueError`。

只提示：窗口与别的存储重叠；同一存储的窗口大小不一致；同一存储的窗口类型不一致（flash 和 ram 混在一起几乎一定是错）。理由：厂商表里确有例外和待核实的地方，阻止保存会让用户无法录入"我还不确定"的数据，违背"芯片数据不全只标记、不删除"。

### D4 导入只认 ADS 注释表，结果先预览

识别两种行格式（都是读文件确认过的）：

- `; 名称  起始  终止 - 长度  (属性)`，如 THA6206 的 `LinkerAdsPf.scat`：`CPU0BTCM  0x30100000  0x30100000 - 0x30130000 (192K)  …`
- `; 名称  起始  起始 + 长度  说明`，如 OS 模板 `scatter.scat`：`CPUXATCM  0x00000000  0x00000000 + 64K  …`

类型、可缓存、核心从行尾的说明文字里读（`Cacheable`、`Non-Cacheable`、`local access`、`CPU0` 等）；读不出的字段留缺省并标待确认，不猜。导入结果先在预览里列出，用户确认才合并；同名项不覆盖，只报告。

导入得到的项一律带 `source: <文件名> 注释表`，并写入 `metadata.unconfirmed.memory_regions`。

### D5 编辑器参照 ECU 资源编辑器的做法

不另起一套交互：页签是一个 `QWidget`，持有工作副本，只写加载器接受的值（"能输入的就能保存、能加载"），变化通过信号通知设计器更新未保存状态和预览。每次修改后立即校验并显示问题列表。

### D6 THA6206 的现有数据只补字段，不动数值

补 `memory`、`window`、`source`。不改任何地址、大小、类型、核心、可缓存。所有项继续在 `unconfirmed.memory_regions` 之下。这是"修复"：按现有机制升 `resource_version`、备份、写历史。

## Risks / Trade-offs

- **归组是推断。** 厂商表按地址窗口列，不列"哪几个是同一块存储"，归组靠名字（`PFLASH0_NORMAL` 与 `PFLASH0_DEVICE`）和地址偏移推断。推断错了，界面上"选存储再选窗口"的呈现会出错。所以归组全部标待确认，编辑器里归组字段可改。
- **只有 THA6206 有数据。** 编辑器和导入对另外两颗芯片只是提供途径；用户得自己有来源。这是有意的。
- **平铺加可选字段让模型略显松散**，换来零迁移。如果以后发现嵌套更合适，再迁移，旧文件可读。

## Migration Plan

1. 先改模型与往返，保证旧 YAML 的 `chip_checksum` 不变（测试覆盖全部库内芯片）。
2. 再加编辑器与导入。
3. 最后改 THA6206 的 YAML（唯一改变内容的文件）。
回退：还原 THA6206 的 YAML 即可，其他都是增量。

## Open Questions

- THA6206 里 CPU 本地别名（`CPUX*`）与每个核的 AXI 区域（`CPU0*`、`CPU1*`）是否算同一块存储？当前从名字推断为"是"，需要用户核对。
- 窗口用途标签是否需要固定的取值集合？本变更先用自由文本。
