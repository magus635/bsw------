## Context

读到的现状（读文件，未运行）：

- 厂商 `LinkerAdsPf.scat`（THA6206）把存储切成执行区域，每个有名字、顺序、对齐（`ALIGN 64`）、起点是前一个区域的界限（`AlignExpr(ImageLimit(X), 64)`）或一个绝对地址；
- `startup.c` 按名字引用其中约四十个区域：复制类（`UNDEFINE_RAM_DATA`、`PRIVATE_DATA_CORE0`……）、清零类（`UNDEFINE_RAM_BSS`、`PRIVATE_BSS_CORE0`……）、栈（`CORE0_USER_STACK`……）、向量与克隆区（`INT_VECTOR_TABLE`、`CODE_CLONE`、`DATA_CLONE`、`BSS_CLONE`）；
- 区域名里的核心号涵盖 `CORE0` 到 `CORE3`，THA6206 只有 2 个核；
- 工程现在是 `工程/generateCode/`、`工程/chips/`，没有集成目录。

## Goals / Non-Goals

- Goals：段到执行区域、执行区域到物理存储的配置；规则自动放置加手动例外；THA6206；切芯片时不丢配置；界面。
- Non-Goals：生成链接文件；容量检查；THA610X、THA6412 的出厂规则；OS 自带 scatter 的处理。

## Decisions

### D1 三层模型

```
段 (Section)             扫描结果，只读：输出段名、种类、核心、可缓存、来源模块
  │  放置
执行区域 (ExecRegion)    配置的一部分
  │  落位
物理存储 (Memory)         芯片的 memory_regions，按 add-chip-memory-editor 分组；只读
    └ 窗口 (Window)       同一块存储的地址窗口，选窗口即决定可缓存与否
```

**执行区域**的字段：

| 字段 | 含义 |
|---|---|
| `name` | 区域名；必需区域由系统给定，自定义区域由用户命名 |
| `memory`、`window` | 落在哪块物理存储的哪个窗口 |
| `kind` | `code`、`const`、`data`、`bss`、`noinit`、`stack`、`reserved` |
| `order` | 在同一窗口内的先后顺序；决定生成时的 `AlignExpr(ImageLimit(前一个), 对齐)` 链 |
| `align` | 对齐字节数，默认 64（厂商脚本一致用 64，栈区域用 8） |
| `required` | 是否必需（只读，由系统决定） |
| `origin` | `required`、`default`、`user`，说明它从哪来 |
| `size_actual` | 预留：编译后的实际大小，本变更不填 |

`kind` 决定它能接收哪些种类的段：`code` 收 TEXT，`const` 收 RODATA，`data` 收 DATA，`bss` 收 BSS，`noinit` 收 BSS（未初始化），`stack` 不收段（栈区域是空区域）。放置时种类不符会被拒绝并说明。

### D2 必需区域的来源

两处合并：

1. **链接符号需求**（`add-link-symbol-needs`）：扫到的代码实际引用的区域名，带用途。这是**事实**：代码引用了就必须有。
2. **THA6206 默认布局**：厂商脚本里存在、但代码不一定显式引用的区域（如 `RAM_CODE`、`LMU*_CACHED_DATA`）。这是**约定**。

扫到的需求优先。若扫不到任何需求（比如没添加 `startup.c` 所在目录），退到默认布局，并在界面上说明"必需区域来自默认布局，未经代码核对"。

必需区域按芯片核数裁剪：名字里 `CORE<n>` 且 n 不小于芯片核数的丢掉（THA6206 的 `CORE2`、`CORE3` 区域不出现）。核数取自芯片的 `metadata.cores.count`。

**裁剪只针对配置，不针对链接文件。** 厂商脚本为未启用的核写了"保留区域"（`EMPTY 0x0 {}`，注释 `reserved region for compiler issue`），因为 `startup.c` 引用了这些名字，链接器要有定义才能通过。所以被裁剪的区域在配置里不可见、不可放段，但生成链接文件时必须作为保留区域补上。这一步在 `add-linker-file-generation` 里做；本变更要保证的是：被裁剪的区域名保留在"被裁剪的必需区域"清单里（`CheckResult` 的需求里本来就有），供生成器取用。

必需区域的 `<名>_LIMIT`：不进配置，生成时自动产出；它不是用户能放段的区域。

### D3 规则

一条规则：

```json
{"name": "核私有 BSS", "match": {"kind": ["BSS"], "core": 0, "name": "*"}, "target": "PRIVATE_BSS_CORE0"}
```

匹配条件按"与"组合：`name`（输出段名的通配）、`kind`、`core`、`cacheable`（`true` 表示可缓存，`false` 表示不可缓存）、`module`。条件缺省即不限。

**优先级**：手动 > 规则。规则按列表顺序，第一条匹配的生效。

**冲突**：一个段被多条同层规则匹配，取第一条，界面上在规则编辑器里标出被遮蔽的规则。目标执行区域不存在或种类不符的规则，标"无效"，不生效。

**默认规则是开放的**（用户已确认）：由我先给出一套 THA6206 的初始规则，使用中发现问题，用户可以直接修改、增加、删除、调整顺序，不需要改代码。具体做法：

- 初始规则放在数据文件 `autosar_configurator/data/memmap/THA6206_LFBGA292_default.json`（文件名用芯片全名），随软件发布，是**出厂默认**；
- 工程第一次打开"配置"页签时，把出厂默认**复制**进工程的 `memorymap.json`，成为这个工程自己的规则，此后用户的修改只作用于这份副本，不会被软件升级覆盖；
- 因此规则只有一份在起作用（工程里的），分层简化为：**手动 > 规则**，规则按列表顺序，第一条匹配的生效。原先"用户规则 > 默认规则"的两层合并成一层；
- 每条规则带 `origin`（`factory` 或 `user`）和可选的 `note`（来源或理由），出厂规则写明依据了厂商脚本里的哪个选择器；
- 用户改了出厂规则，该条标记为"已修改"（保留原值以便比较）；
- "恢复出厂规则"按钮：把规则列表整体换回出厂默认，换之前先预览会丢失哪些用户修改，确认才执行；手动放置不受影响；
- 软件以后升级了出厂规则，不自动覆盖工程里的副本；规则编辑器里提示"出厂规则有更新"，由用户选择是否合并。

**出厂初始规则（THA6206）**，来自厂商 `LinkerAdsPf.scat` 里的选择器，是我读脚本总结的，用户可以改：

| 条件 | 目标 |
|---|---|
| BSS，核 n，可缓存 | `PRIVATE_BSS_CORE<n>` |
| DATA，核 n，可缓存 | `PRIVATE_DATA_CORE<n>` |
| TEXT，核 n | `PRIVATE_CODE_CORE<n>` |
| BSS／DATA，不可缓存（无核） | `GLOBAL_UNCACHED_BSS`／`GLOBAL_UNCACHED_DATA` |
| BSS／DATA，名含 `_lmu<n>` | `LMU<n>_CACHED_*`（不可缓存则 `LMU<n>_UNCACHED_*`） |
| BSS，未初始化 | `UNCLEAR_RAM_BSS` |
| TEXT／RODATA（无核） | `EX_CODE`／`EX_CONST_DATA`（在 PFLASH） |
| 其余 DATA／BSS | `UNDEFINE_RAM_DATA`／`UNDEFINE_RAM_BSS` |

**这套初始规则我没有逐条与厂商脚本核对**，上表是我读脚本时看到的选择器模式。因为规则是开放的，"没核对"的代价从"阻塞开工"降为"用中发现问题再改"，所以**不再把与厂商脚本对照作为开工的前置条件**。对照仍然有用，作为可选的验证放在最后（tasks 4.3），要读厂商文件，运行前先征得用户同意。界面上出厂规则标注"初始规则，未与厂商脚本逐条核对"，直到用户确认。

### D4 状态

每个段有且只有一个状态：

| 状态 | 含义 |
|---|---|
| 规则 | 被某条规则（默认或用户）放置 |
| 手动 | 用户手动指定，忽略规则 |
| 未放置 | 没有规则匹配，也没有手动指定 |
| 待重新放置 | 目标执行区域已不存在（切芯片后） |

手动放置是一条 `(段名 → 区域名)`，存在配置里；移除手动放置，段回到规则的结果。

### D5 配置的存放

决定：存在 `工程/IntegrationProject/linkedFile/memorymap.json`，生成的链接文件在 `工程/IntegrationProject/linkedFile/<编译器>/` 下。

- **目录名 `IntegrationProject` 和 `linkedFile` 是常量**，各在一处定义，路径随工程保存且可改。理由：集成工程的整体目录结构还没设计，这里先用你给的名字，以后整体设计出来再调整，只改常量。
- **配置是纯文本 JSON**：可进版本管理、可 diff。
- 文件里带 `schema` 版本号和 `chip` 名；读取时若芯片不同，按 D6 处理。

### D6 切芯片

沿用"芯片变更预览"（`project-chip-selection` 里的现有机制），预览新增"内存布局"一节，列出：

- 仍然有效的放置（执行区域在新芯片里还能落位）：保留；
- 对不上的放置：标"待重新放置"，列出段名和原目标；
- 必需区域的变化：新增的、消失的（标"不再需要"，保留在配置里）；
- 手动放置的：全部保留，对不上的也标"待重新放置"。

"对得上"的判断：执行区域所在物理存储在新芯片里存在，且该窗口的可缓存、核心属性与原来一致。不一致就算对不上，因为静默换一个窗口会悄悄改变缓存属性。

沿用"芯片数据不全只标记、不删除"的约定：任何情况下配置里的放置都不会因切芯片被删除。

### D7 界面

并入工作台，新增第三个页签"配置"。

- 左：段表，列为输出段名、种类、核心、模块、状态、当前目标；过滤：模块、核心、种类、状态；
- 右：树：物理存储 → 窗口 → 执行区域；执行区域上显示"必需"标记和已放置的段数；
- 操作：拖拽（左到右）、选中后按"+"（放到所选执行区域）、"−"（移出，回到规则）；多选批量；
- 放置前检查：种类不符、目标不存在，直接拒绝并给出原因；
- 每次改动后立即把改动存入内存中的配置，配置页签上的状态随之更新。诊断和布局页签对照的是磁盘上的链接文件，生成之前不会变；页签上写明这一点，避免用户以为放置已经生效；
- "保存配置"写入 `memorymap.json`；未保存的改动在关闭窗口时询问。

不在界面里做的：改执行区域的顺序和对齐（第一版用默认顺序，来自默认布局；高级调整放到以后）；新增、删除必需区域（不允许）。自定义区域可以增删。

### D8 不碰 OS 自带的 scatter

OS 的 `scatter.scat`、`Os_link_Lcfg.c`、`Os_mpu_Lcfg.c` 保持原样。布局配置里 OS 的段（来自 `Os_memmap.h`）和其他段一视同仁，但 OS 自带 scatter 里的执行区域名（来自 OS 的 `MemoryBlock`）如果与本配置的区域重名，**不冲突检测**——这是下一个变更生成链接文件时必须面对的问题，现在只记在 Open Questions。

## Risks / Trade-offs

- **出厂规则没有逐条核对。** 如上，D3 已说明。因为规则开放可改，这不再阻塞开工；核对作为可选验证。界面上标注出厂规则的状态。
- **执行区域的顺序和对齐第一版不可编辑。** 好处是模型简单；坏处是用户想调整布局时做不到。我认为大多数场景用不到，暂不做。
- **必需区域靠代码扫描 + 默认布局。** 没添加 `startup.c` 所在目录时，必需区域退到默认布局，可能多或少。界面会说明来源。
- **"待重新放置"的段在生成时怎么办**，属于下一个变更；本变更只保证它们不丢。
- **配置存工程目录，多人协作时 JSON 可能冲突。** 文本 JSON 加稳定排序（按名称）减少无谓的 diff。
