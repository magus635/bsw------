## Context

`add-linker-file-generation` 的生成器（`plan.py`、`generators/ads.py`）只认识三种信息：区域在哪个窗口、在窗口里的先后、种类。所以它生成的每个窗口都是"第一个区域从窗口起点开始，后面的一个接一个"。用户想要的布局只要不是这个形状，就配不出来。

用户的定位（2026-11-03）：生成器是权威，厂商脚本只是可选的导入源。所以本变更的目标是**让配置能表达用户想要的布局**，而不是让结果和某个厂商脚本一样。

## Goals / Non-Goals

- Goals：执行区域的起点、大小、所属加载区域、界限对齐都可配；从已有 `.scat` 导入布局作为起点；出厂数据改正与补齐；文档里去掉"厂商脚本是标准答案"。
- Non-Goals：容量检查；其他编译器；非 ADS 文件的导入；ADS 高级语法。

## Decisions

### D1 起点三选一，缺省不变

`ExecRegion.start_mode`：

| 值 | 含义 | ADS 写法 |
|---|---|---|
| `after`（缺省） | 同一窗口里接在上一个区域之后；窗口里的第一个区域从窗口起点开始 | `AlignExpr(ImageLimit(<上一个>), <对齐>)` 或 `<窗口>_ADDRESS` |
| `offset` | 窗口起点加 `offset` | `<窗口>_ADDRESS+0x20000` |
| `address` | 固定地址 `address` | `#define <区域>_ADDRESS 0x30129000`，再引用 |

`address` 不在所选窗口里时提示（不阻止：用户可能有意用别名地址），并在生成前的检查里作为警告列出。

区域在窗口里的顺序仍由 `order` 决定；一个 `offset`/`address` 区域之后的 `after` 区域，接在它后面。这正好表达厂商的栈：`CORE0_USER_STACK` 用 `address`，后面六个栈用 `after`。

### D2 大小：可选，没有就按现在的规则

`ExecRegion.size`：普通区域写成上限，栈与保留区域写成 `EMPTY` 长度。缺省时：普通区域取窗口大小，栈 `0x1000`，保留区域 0。仍不检查容量。

### D3 多个加载区域，没有配置时行为不变

`MemoryMapConfig.load_regions: List[LoadRegion]`，每个有名称、所在窗口、大小上限。`ExecRegion.load_region` 指定所属；缺省是第一个加载区域。

列表为空时，生成器像现在一样造一个 `ROM_CODE`。所以旧配置的生成结果逐字节不变（用现有的确定性测试守住）。

一个加载区域里的执行区域按"窗口顺序、再按 `order`"排列，与现在一致；不同加载区域按列表顺序写出。

### D4 界限区域的对齐

`ExecRegion.limit_align`，缺省 64。界限区域写成 `<名>_LIMIT AlignExpr(ImageLimit(<名>), <limit_align>) EMPTY 0x0 {}`。原来跟随区域本身的对齐（栈因此是 8），改为缺省 64；旧配置因此会有字节变化——**这是本变更里唯一的、有意的输出变化**，在任务里单独列出并测试。

### D5 导入：从一个 `.scat` 得到配置的起点

复用 `scatter.parse_scatter`（检查器已经在用、已有测试），不另写解析器。转换规则：

- 加载区域 → `LoadRegion`（窗口按其基址落在芯片哪个窗口；落不进任何窗口的报告为"不能导入"）；
- 执行区域 → `ExecRegion`：
  - 窗口：基址落在哪个窗口（与检查器 `region_at` 同一规则）；跟随上一个区域的，取上一个的窗口；
  - 起点：解析出"跟随谁"的是 `after`；基址是 `<define>+偏移` 的是 `offset`；基址是绝对数的是 `address`；
  - 种类：`EMPTY` 区域名含 `STACK` 的是栈，其余空区域是保留区域；有选择器的按选择器里出现的段种类推断（`+RO-CODE`/`.mcal_text_*` → code，`+RO-DATA`/`.mcal_const_*` → const，`+ZI`/`+BSS`/`_bss_` → bss，`_no_init_` → noinit，其余数据 → data）；推不出的标"待确认"并列在报告里；
  - 名字以 `_LIMIT` 结尾的空区域不导入（生成器会自己产出）；
- 选择器：
  - `*(.name)`、`*(+属性, .name)`：每个段名变成一条手动放置；
  - 通配（`*(+BSS)`）、`.ANY`、按文件（`exception.o(...)`）、`+First`：不导入为放置，列在报告的"不能导入"里，说明原因；
- 已有同名区域：不覆盖，报告；同一段已有手动放置：不覆盖，报告。

预览先给出：新增区域、跳过的同名区域、新增的手动放置、跳过的放置、不能导入的选择器。确认后才写进配置。导入不改规则。

导入的结果是**起点**，不是约束：之后在界面里怎么改都行，再生成时以配置为准。

### D6 出厂数据：改正与补齐

- `INT_VECTOR_TABLE` 改到 `CPUXATCM` 窗口（地址 `0x0`），这是我写出厂数据时的错误；
- 补上 `CODE_CLONE`、`DATA_CLONE`、`BSS_CLONE`、`RAM_CODE`、`EX_CODE_CORE1`、`EX_CONST_DATA_CORE1`、`DFLASH_DATA`，各自的窗口、种类、顺序；
- `CORE0_USER_STACK`、`CORE1_USER_STACK` 用固定起点，各栈带大小 `0x1000`；
- `UNDEFINE_RAM_DATA` 用偏移 `0x20000`；
- DFLASH 单独一个加载区域。

这些值都是"出厂起点"，来源注释写明，用户可以改。

### D7 去掉"厂商脚本是标准答案"

在两个旧变更的设计里改掉以下说法：

- `add-linker-file-generation` D6/D7：自检是"配置与生成物自洽"的证明，与厂商脚本无关；D7"与厂商脚本对照"改为"可选：导入一个已有的脚本作为起点"；
- `add-memory-layout-config` D3：出厂规则"依据厂商脚本"保留为来源说明，但"用厂商脚本核对出厂规则"不再是验证条件。

## Risks / Trade-offs

- **界限对齐缺省改为 64 会改变旧配置的输出字节。** 有意为之，单独测试并在任务里写明。
- **导入的种类推断可能不准。** 推不出的标待确认；推出的也可以在界面里改。
- **固定地址落在窗口外**只警告不阻止，用户可能配出无效布局。生成后的自检仍会报出放置问题；真实链接仍需用户做。

## Migration Plan

1. 先改模型（新字段，旧文件可读），守住"旧配置输出不变"（除界限对齐）；
2. 再改生成器；
3. 导入；
4. 出厂数据；
5. 界面；
6. 文档措辞。

## Open Questions

- 界限对齐缺省值：64（与厂商一致）还是跟随区域对齐（现在的实现）？本设计选 64，用户可改。
- 导入时，厂商脚本里的注释是否要带进区域的说明字段？本变更不带。
