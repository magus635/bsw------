二、 核心机制：“定义-值”分离 + “模板-工程”分离

依据：vBaseEnv_bswmd.arxml、vBaseEnv_THA6_pre.arxml、TechnicalReference_DaVinciConfigurator_WorkflowOverview.pdf（第 3.1.1~3.1.3 节）
维度定义侧（Schema + 实现元数据）值侧（模板值 → 工程活配置）
XML 元素ECUC-MODULE-DEF + BSW-IMPLEMENTATIONECUC-MODULE-CONFIGURATION-VALUES
文件命名_bswmd.arxml（MCAL 为 Copy__THA6206_LFBGA292.arxml）模板：_pre.arxml / _rec.arxml；活配置：Config/ECUC/*_ecuc.arxml
数量关系每个模块 1 个 ECUC-MODULE-DEF对应 0 ~ N 个 pre/rec（按通用层、编译器、芯片族拆分；如 Com 无 pre/rec，vLinkGen 有 5 个 pre/rec）
生效时机与读写属性加载工程时构建元模型与校验规则• _pre.arxml（Pre-configuration）：每次加载工程（Project Load）及 Project Update（第 6 步）时动态应用到内存模型并只读锁定（灰显不可改），保存工程时同步持久化到 *_ecuc.arxml。
• _rec.arxml（Recommended）：仅在新建模块/容器（Object Creation）或 BaseEcuC 初始化（第 4 步）时一次性赋予初值，之后用户可自由修改。
• 冲突优先级：Pre-configuration > Derived（系统描述派生值）> Recommended / Default。

跨文件双向引用闭环

  • 跨文件合并原理：AUTOSAR 允许多个 .arxml 声明同名的 <AR-PACKAGE>（如 /MICROSAR）。DaVinci 加载 SIP 时会将所有文件中的 /MICROSAR 包合并到同一逻辑命名空间下（Additive Merge，见 WorkflowOverview.pdf 第 2 章），因此 vBaseEnv_bswmd.arxml 中引用 /MICROSAR/vBaseEnv_Pre，即可自动解析到芯片子目录 vBaseEnv_THA6_pre.arxml 中的同名对象。

三、 模块集成的两条来源通道（22 Vector + 6 MCAL）

依据：StartApplication.ecuc.arxml、StartApplication.dpa、UserManual_3rdParty-MCAL-Integration.pdf（第 2.4 节）、MicroSar工程应用及MCAL驱动升级说明.md

来源 A：Vector MICROSAR 模块（当前工程激活 22 个）

  • 模块列表：vSet、Os、Det、EcuC、BswM、EcuM、Rte、vBRS、vBaseEnv、Crc、vLinkGen、MemMap、VTTMemMap、CanIf、ComM、CanSM、Com、PduR、CanTrcv、VX1000、Dcm、CanTp。
  • 包路径：全部位于 /ActiveEcuC/<模块>。
  • DEFINITION-REF：指向 /MICROSAR/<模块>（两个带子包的特例：/MICROSAR/CanTrcv_Tle9255/CanTrcv、/MICROSAR/VTT/VTTMemMap）。
  • MODULE-DESCRIPTION-REF：22 个模块全部具备，指向 /MICROSAR/<模块>_Impl（其中 VX1000 为 /MICROSAR/VX1000_Impl_Default）。
  • 代码生成器：各组件目录下的 GeneratorMsr/.jar（针对 DaVinci Configurator 5）和 GeneratorDvC6/.jar（针对 DaVinci 6）。

来源 B：外部工具模块——EB Tresos MCAL（当前工程激活 6 个）

  • 模块列表：Mcu、Port、Dio、Spi、Resource、Can。
  • 定义文件来源：由 ThirdParty/McalIntegrationHelper/mcalintegrator_cmd.exe 根据 MIPconfig.xml 从 ThirdParty/Mcal_Tha62x/Supply/ 中提取并打补丁，生成到 Components/Mcal_Tha62x/BSWMD/Copy__THA6206_LFBGA292.arxml，同时附带 Vector 编写的推荐配置 _bswmd_rec.arxml 和内存映射 *_MemMap.arxml。
  • DEFINITION-REF：6 个模块全部指向 /THA6_AS440_FuSa/<模块>。
  • MODULE-DESCRIPTION-REF：仅 Mcu、Port、Dio、Spi 4 个模块具备（指向 /THA6_AS440_FuSa/<模块>_Impl）；Can 和 Resource 无此标签。
  • 包路径差异（Can 的特殊性）：
  • Mcu、Port、Dio、Spi、Resource 5 个模块是从 Tresos 导出后导入 DaVinci 的，因此保留了 Tresos 的顶层包名（/Mcu/Mcu、/Port/Port、/Dio/Dio、/Spi/Spi、/Resource/Resource）。
  • Can 位于 /ActiveEcuC/Can：因为在 StartApplication.dpa 中配置了 <ComControllerMapping ClusterPath="/Cluster/MotorDomain" DefintionPath="/THA6_AS440_FuSa/Can"/>，它是随 DBC 通信矩阵由 DaVinci 的 BaseEcuC 生成器直接派生在 /ActiveEcuC 包下的。
  • MCAL 配置与生成的两条工作流模式（见 UserManual_3rdParty-MCAL-Integration.pdf 第 2.4 节）：
  • Single/Mixed Tool 标准通道（DaVinci 调 Tresos_proxy）：在 DaVinci 中编辑 *_ecuc.arxml，生成时由 Tresos_proxy.jar 根据 Settings_Tresos.xml 和 Settings_ExtGen_Tha62x.xml 调用后台 tresos_cmd.bat 一次性生成代码（GenerateModulesAtOnce="true"），并通过 prepare_output_Tha62x.xsl 转换输出。
  • 本工程升级 MCAL FuSa V1.2.0 时的 Split/手动转换通道：如 MicroSar工程应用及MCAL驱动升级说明.md 所记，升级 MCAL 时通过脚本 convert_ecuc_to_xdm.py 将 *_ecuc.arxml 中的 /THA6_AS440/ 替换为 /THA6_AS440_FuSa/，并调用 tresos_cmd.bat legacy convert 单向转为 .xdm（Can.xdm 需将包名 ActiveEcuC 手动改为 Can），拷贝至 TresosMcalProject/THA6206_LFBGA292_AS440/config/ 在 Tresos GUI 中编译生成到 Appl/GenData/include/ 与 Appl/GenData/src/。

四、 主索引、双 EcuC 模型与生命周期归档

依据：StartApplication.dpa、StartApplication.ecuc.arxml、StartApplication.ecuc.Initial.arxml、TechnicalReference_DaVinciConfigurator_WorkflowOverview.pdf（第 3 章）

1. 主索引 StartApplication.ecuc.arxml + .dpa <EcucSplitter>

  • StartApplication.ecuc.arxml 中的 ECUC-VALUE-COLLECTION（/ActiveEcuC/ActiveEcuC）是当前工程激活模块的唯一权威注册表：
  • <ECU-EXTRACT-REF> 指向系统描述同步路径 /COM/VECTOR/CFG/WORKFLOW/SYSDESC/SYNC/SYSTEM。
  • <ECUC-VALUES> 包含 28 个 ECUC-MODULE-CONFIGURATION-VALUES-REF（22 Vector + 6 MCAL），与 StartApplication.dpa <EcucSplitter> 中的 28 个 <Splitter> 严格一一对应（开启了 OwnFileForEachInstance="true"，故每个模块拆分为独立的 StartApplication_<模块>_<模块>_ecuc.arxml）。
目录文件 ≠ 激活模块：Config/ECUC/ 目录下实际有 30 个 StartApplication_*_ecuc.arxml 文件。多出的 StartApplication_E2E_E2E_ecuc.arxml（有配置内容）和 StartApplication_vItaSip_vItaSip_ecuc.arxml（<ELEMENTS> 为空）均未在主索引和 .dpa Splitter 中登记，属于游离文件，不参与校验与生成。

2. ActiveEcuC 与 InitialEcuC（Derived）双模型对比机制

在 StartApplication.dpa 中定义了两个 ECUC 根包：

角色.dpa 标签对应文件根包路径作用与内容
ActiveEcuC<Active>StartApplication.ecuc.arxml（拆分到 28 个单模块文件）/ActiveEcuC/ActiveEcuC用户日常编辑、参与校验与代码生成的活配置（28 个模块）。用户手动修改过的派生参数会标记为 User-Defined。
InitialEcuC (BaseEcuC)<Derived>StartApplication.ecuc.Initial.arxml（单文件，5566 行）/InitialEcuC/InitialEcuC通信矩阵/系统描述派生基线：仅包含由 MCU.dbc / SystemExtract.arxml 自动推导出的 10 个通信/诊断相关模块（Can、CanIf、CanSM、CanTp、Com、ComM、Dcm、EcuC、EcuM、PduR，带 DV:SoftDerived 注解）。用于在下次更新 DBC 时与 ActiveEcuC 做三方合并（保留用户的 User-Defined 修改，仅更新未锁定的派生值）。

3. 删除归档 .workflow/DeletedModules/

  • 当在 DaVinci 中移除某个模块时，工具将其从主索引和 <EcucSplitter> 中移出，并将原配置自动备份至 .workflow/DeletedModules/<模块>_<时间戳>.ecuc.arxml（当前存有 CanNm、Nm、Com、PduR、CanTp 共 13 个历史备份文件）。
  • 注意：该目录仅代表“历史上曾发生过删除操作”，不代表模块当前不存在——例如 Com、PduR、CanTp 在 2026-05-22 被删除备份后，现已重新导入并激活在主索引中。

六、 模块完整生命周期

一句话总结

DaVinci Configurator 是一个多源模型驱动的集成配置中枢：它以 StartApplication.dpa 为总控，以 Components/ 与 DemoComponents/ 中的“定义（_bswmd）+ 预配置锁定值（_pre）+ 推荐初值（_rec）”为基础，通过 ECUC-VALUE-COLLECTION 主索引和 EcucSplitter 统一管理 *22 个 Vector BSW 模块（/MICROSAR/） 与 6 个 Tresos MCAL 模块（/THA6_AS440_FuSa/）* 的活配置；利用 InitialEcuC（通信矩阵派生基线）实现输入变更时的无损三方合并，利用 DeletedModules 实现模块删除留痕，通过 vBaseEnvTestedDerivativeRef 切换芯片硬件变体，最终协同 Vector 生成器与 EB Tresos 输出全套配置源码、链接脚本与构建配置。
